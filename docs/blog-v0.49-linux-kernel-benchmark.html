v0.49.0 benchmark: Codixing on the Linux kernel

We pointed v0.48.0 at Linux 6.6 (71,025 indexed files) and measured what an agent actually waits for and reads. Most of it was too slow or too large. v0.49.0 is the result of fixing what we found. Here are the before-and-after numbers and how to reproduce them.

The setup

Everything below was measured on a 4-vCPU, 15 GB Linux cloud container with a warm page cache, in BM25-only mode (no embeddings). We used three corpora: this repository (about 370 files), Django 5.0.6 (3,851 files) and Linux 6.6 (71,025 files). Times are the wall clock of the whole CLI process, with no daemon, unless stated. Token counts use cl100k_base.

Retrieval quality comes from 62 queries with known answers: 30 identifier lookups and 32 natural-language tasks. A hit means a result from the expected file appears at that rank or better.

Read the numbers with that in mind: the query sets are small and written by one reviewer. The gaps are large relative to that noise, but treat the exact percentages as approximate. The harness is in the repository so you can run it on your own code.

Cold start: every call used to reopen the whole index

On the kernel, v0.48.0 spent about 4.5 s and 900 MB just opening the index for every CLI call. ripgrep answered the same literal query in 0.3 s. v0.49.0 opens read-only engines lazily: chunk metadata and the dependency graph are decoded only when a command needs them, and a BM25 search reads its hit fields from stored Tantivy values.

On indexes of 20,000+ files the CLI now starts a read-only daemon in the background. Once it is warm, search takes 10–26 ms, ask 100–195 ms and graph --map 76 ms. Set CODIXING_NO_AUTO_DAEMON=1 to opt out.

Retrieval: the recommended entry point was the weakest one

The biggest surprise was that ask, the command we tell agents to start with, found the right file far less often than plain search. It pinned symbols for ordinary long words and used a different retrieval path. Now it runs the task through the same path as search. Natural-language BM25 queries also gained a re-rank that rewards query terms in the path, terms that occur together in one identifier, and evidence spread across a file.

On the kernel, identifier lookups needed C-specific work. Struct references without a body are no longer indexed as definitions. Attribute macros that break the grammar (__alloc_size(1), __printf(2, 3)) are blanked before parsing, so kmalloc is found. Function-like #define macros and SYSCALL_DEFINEn bodies are now symbols.

Natural-language search without embeddings still depends on the query sharing words with the code. One of the ten Linux tasks, about the out-of-memory killer, is still missed because the code says oom.

Output: tokens that carried no information

A fast wrong answer is bad, and so is a correct answer buried in padding. On the kernel, a single v0.48.0 symbols task_struct call returned 126,278 tokens. v0.49.0 returns 1,158: definitions only, best match first, capped at 50 rows. callers include/linux/slab.h dropped from 8,254 to 1,151 tokens. ask now prints compact text by default, about a third of the previous size.

For identifier tasks, the median tokens an agent reads before it sees the expected file are now 59 on this repository, 42 on Django and 65 on Linux. rg -nw prints 5,127, 2,909 and 5,471 for the same names.

Incremental sync

Every checkpoint used to rewrite all chunk metadata, which is 93 MB on the kernel. A checkpoint that touches few files now writes a changed-file overlay, 1.6 KB for one file. The persist phase of a one-file sync went from 4.7 s to 2 ms.

A no-op sync on Linux still takes about 3.5 s because it opens a writable engine. That is the next thing to fix.

Today's run on the release commit

On the commit we released as v0.49.0, on the same kind of 4-vCPU host:

  • Retrieval gate on this repository: identifier hit@1 8/8 (MRR 1.00); natural-language hit@10 12/12 (MRR 0.73).
  • bench-tokens, definition plus blast radius of IndexStore: 1,896 tokens against 5,092 for grep plus file reads, 62.8% fewer. The answer was present in every step.
  • Criterion: BM25 identifier search in 116 µs; search across a 10K-file repository in 10.8 ms; trigram grep on a selective literal 6.9× faster than a full scan at 10K files.

Both checks now block CI. benchmarks/retrieval_gate.py runs answer-checked task sets against this repository and a checksum-pinned Django, and fails when hit rates drop or when ask trails search.

Reproduce it

curl --proto '=https' --proto-redir '=https' -fsSLo \
  /tmp/codixing-install.sh https://codixing.com/install.sh &&
sh /tmp/codixing-install.sh

codixing init .
codixing bench-tokens .
python3 benchmarks/retrieval_gate.py \
  benchmarks/retrieval/tasks_self.json .

The full review, with the root cause of each finding, is codixing-review-2026-11-10.md. Its harness and task files are in benchmarks/review-2026-11-10/. Codixing v0.49.0 is on GitHub Releases and as codixing-mcp@0.49.0 on npm.

Heads-up if you upgrade: line numbers are now 1-based everywhere, including context --line and the MCP read_file ranges, and the default search, symbols and ask output formats changed. The changelog lists every change.
